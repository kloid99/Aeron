## 서술 원칙 (기존 3원칙 유지 + 1 추가)

1. **주어는 오케스트레이터** — 로봇이 아니라 KT 오케스트레이터가 정비 지식·AI·로봇·정비사를 연결해 작업을 끝까지 통제한다.
2. **정상 흐름만 보여주지 않는다** — 예외 처리(재촬영·반려 복귀·안전 전환)가 단순 자동화와의 차별점이다.
3. **비전 AI의 역할 제한** — 촬영 품질 확인과 이상 후보 표시까지만. 최종 판단·승인은 항상 정비사(HITL).
4. **(추가) 챗봇의 집은 서버, 접점은 정비사 디바이스** — 지식 두뇌는 KT 클라우드에 있고, 정비사 디바이스(화면+음성)가 접점이다. 디바이스와 로봇은 서버와 병렬 통신한다. 로봇은 대화 접점이 아니라 촬영 엔드포인트다.

각 단계는 세 줄로 서술한다: **상황** (무슨 일이 일어나는가) / **판단** (오케스트레이터가 무엇을 결정하는가) / **화면** (정비사 디바이스에 무엇이 보이는가).

## A. 작업 시작

**1. 작업지시 하달·접수**

- 상황: 중앙 정비관리 시스템에서 담당 정비사가 이미 지정된 Work Order가 하달된다. 오케스트레이터는 접수하고 상태를 '수락 대기'로 전이한다. (정비사 배정은 중앙 관리자의 영역 — 오케스트레이터는 관여하지 않는다)
- 판단: 없음. 상태 전이만.
- 화면: 작업 알림 카드 — 기체·구역·작업 내용·우선순위. 하단 [작업 수락] 버튼.

**2. 작업 수락**

- 상황: 정비사가 [작업 수락]을 누르면 작업이 시작된다. Work Order 상태 '진행' 전이.
- 판단: 없음.
- 화면: 작업 상세 화면으로 전환.

**3. 절차·주의사항 제시 + 상시 질의**

- 상황: Knowledge Agent가 **작업지시 텍스트 기반**으로 관련 절차·안전 주의사항을 검색해 제시한다. 챗봇은 이 시점부터 **작업 전 구간 상시** 활성 — 정비사는 어느 단계에서든 화면 또는 음성으로 질의하고("이 부품 토크 값?"), 단계별 안내를 음성으로 받을 수 있다.
- 판단: 없음 — 오케스트레이터는 검색을 요청하고 결과를 전달할 뿐, 지식 해석은 하지 않는다 (지식은 AI, 결정은 규칙, 최종 판단은 사람).
- 화면: 절차 체크리스트 + 안전 주의사항 배너(상단 고정) + 챗봇 질의창(음성 입출력 지원). 답변에는 근거 문서 출처 표시.
- ※ 유사 사례는 이 단계에서 제시하지 않는다 — 검색 입력(사진)이 아직 없기 때문. 8단계에서 등장.

**4. 작업 분해·주체 후보 제시**

- 상황: 오케스트레이터가 Work Order를 Task Step으로 분해하고, 각 단계에 수행 주체 후보(정비사/AI/로봇)를 표시한다.
- 판단: 분해와 후보 표시까지만 — 촬영 주체의 최종 결정은 5단계에서 정비사가 한다.
- 화면: 단계 목록 타임라인 — 단계별 주체 아이콘과 상태 표시. 정비사가 작업 전체 그림을 시작 전에 본다.

## B. 촬영 실행

**5. 촬영 명령 (실행 게이트 + 지식 기반 파라미터)**

- 상황: 정비사가 결함 의심 부위의 촬영을 로봇에 지시하거나("이 부위 찍어줘") 직접 촬영을 선택한다. 절차상 요구 컷 목록은 참고 정보로 표시된다.
- 판단: 로봇 지시 수신 시 ① **실행 게이트** — 로봇 가용성(텔레메트리 정상) 검사를 통과해야 실행. ② **온톨로지에서 해당 부위의 촬영 스펙(접근 방향·요구 각도·조명 여부)을 읽어 Skill Request 파라미터로 변환**해 발행. — *사람은 부위만 말하고, 어떻게 찍는지는 지식이 안다.* 게이트 불통과 시 사유와 함께 직접 촬영 안내.
- 화면: 요구 컷 참고 목록 + [🤖 로봇 촬영 지시] / [📷 직접 촬영·업로드] 버튼. 로봇 불가 시 버튼 비활성 + 사유 표시.
- ◆ **촬영 스펙의 실체 (v1.1):** 데이터정의서 v3.6 검사위치 클래스의 '촬영 스펙(접근방향·요구각도·조명필요)' 속성 — 값은 🔧 팀 정의 + 2차 인터뷰 보정. 왜 이 세 필드인가의 물리 근거: **결함은 각도가 만든다** — 산업 육안검사 통상 기준 대상면 600mm 이내·시야각 30°↑·1,000럭스↑, 균열은 5~45° **스침 조명**에서 그림자로 드러난다(항공 GVI/DVI는 정량 미규정 — '통상 기준'으로만 인용). 상세: `72_왜로봇팔인가_물리커버리지_v1.md`

**6. 촬영 수행 (병행 작업)**

- 상황: (로봇 경로) 로봇이 검사 위치로 이동·자세 조정·조명·촬영을 수행하고 Execution Event로 상태를 보고한다. (직접 경로) 정비사가 촬영 가이드에 따라 플랫폼 카메라 또는 스마트폰으로 촬영·업로드한다.
- 판단: 없음 — 실행 감시만. **로봇 촬영 중 정비사는 디바이스로 다음 단계 안내를 받으며 다른 Task Step을 병행하고, 오케스트레이터가 두 실행 흐름의 상태를 관리한다.** (정비사는 로봇을 기다리지 않는다 — 로봇 속도가 병목이 되지 않는 구조)
- 화면: (로봇) 실행 상태 실시간 표시 — 현재 동작·진행률·시뮬레이션 상 로봇 위치, [긴급 정지] 상시 노출. (직접) 촬영 가이드 — 요구 부위·각도·예시 이미지, 업로드 버튼.
- ◆ **로봇 실체 (v1.1):** **Indy7 + Moby 구조 기반으로 고정**(v3.6 확정분 — Indy12는 자중 57kg으로 Moby 적재 40kg 초과, 공식 탑재 옵션도 Indy7 시리즈). IndyEye 작동거리 **5~70cm** — 근접 정밀 촬영이 이 카메라의 기본 작업 영역이고, 반복정밀도 0.1mm가 "같은 각도 재현 = 변화 비교"의 전제다. ⚙️ 도달 높이(리치 1.2m vs 작업반경 0.8m 정의)·검사 포인트당 소요시간은 미확정 — 공식 3D CAD 확인·PoC 실측 전까지 산출물에 수치를 쓰지 않는다.

**7. 품질 확인·재촬영 / 로봇 예외**

- 상황: 촬영물은 출처 무관하게 Evidence로 등록되며 품질 검사를 거친다.
- 판단: **품질 미달 시** — 로봇 경로는 자동 재촬영, 직접 경로는 재촬영 요청 알림. 재시도 상한(⚙️ PoC 실측으로 확정) 초과 시 사람에게 전환. **로봇 오류·응답 시간초과 시** — 안전 정지 명령 후 해당 촬영을 직접 촬영으로 전환.
- 화면: 품질 결과 — 통과 시 썸네일, 미달 시 사유(흐림·조도 부족 등)와 재촬영 안내. 로봇 예외 시 "직접 촬영으로 전환되었습니다" 알림.

## C. 판정·전이

**8. 분석 결과·유사 사례 제시**

- 상황: 품질 통과된 Evidence에 비전 AI가 이상 *후보*를 마킹한다(최종 판정 아님). 그 사진이 임베딩 검색의 입력이 되어 유사 사례 후보를 찾고, 부위·결함 유형 메타데이터로 필터링해 제시한다.
- 판단: 없음 — 분석·검색 요청과 전달만.
- 화면: 사진 + 이상 후보 마킹 + 유사 사례 카드(유사 사진·결함 유형·당시 판정과 조치) + "참고 정보이며 판정은 정비사가 합니다" 고지 + 챗봇 질의창.
- ◆ **데이터 실체 (v1.1):** 이상 후보 마킹 = **결함후보(DefectCandidate) 생성.** AI·로봇은 결함후보만 만들 수 있고 결함(Defect)은 9단계 정비사 판정으로만 확정된다 — 서술 원칙 3이 스키마로 강제되는 지점(v3.6). 유사 사례 카드의 검색 대상 = **사례(상위)** 클래스: 외부사례(FAA SDR)와 검증사례(12단계 환류 생성분)를 한 질의로 답한다.

**9. 정비사 판정**

- 상황: 정비사가 정상 / 이상 / 재검사 중 하나를 판정한다. Human Decision으로 기록된다.
- 판단: 판정 대기 시간초과 시 작업을 '보류' 상태로 표시 (독촉·재배정은 하지 않음 — 중앙 관리자 영역).
- 화면: 판정 버튼 3개 + 판정 사유 입력(선택, 음성메모 가능). 이상 선택 시 결함 유형 선택지 제시.

**10. 판정에 따른 전이**

- 상황: 오케스트레이터가 판정 결과에 따라 다음 상태를 결정한다.
- 판단: 정상 → 다음 Task Step 또는 종료 판단으로. 이상 → 후속 조치 단계 생성(수리 작업지시 연계는 범위 밖 — 기록까지만). 재검사 → **5단계(촬영 명령)로 복귀**.
- 화면: 전이 결과 안내 — "다음 단계로 이동합니다" / "재검사: 촬영 단계로 돌아갑니다".

## D. 기록·환류

**11. Work Card 초안·승인**

- 상황: 사진·작업시간·로봇 실행 로그·판정 결과(촬영 출처 포함)가 Work Card 초안으로 자동 조립되고, 정비사가 확인·수정 후 승인 또는 반려한다. 승인 시 Work Record 확정, 작업 종료.
- 판단: **완결성 게이트** — 필수 항목(요구 컷 Evidence 존재·품질 통과·판정 기록 등) 검사를 통과한 것만 승인 요청으로 올린다. `⚙️ 설계 반영 · PoC 미구현 — PoC에서는 승인 단독으로 종료, 실도입 시 필수 필드 검증 규칙으로 구현` 반려 시 해당 항목 재작성 상태로 복귀.
- 화면: Work Card 초안 — 자동 채움/수정 가능 필드 구분. [승인] / [수정 후 승인] / [반려]+사유.

**12. 지식 환류**

- 상황: 승인된 Work Record가 사례 라이브러리에 등록된다 — 사진은 임베딩 인덱스로, 판정·조치는 메타데이터로. 다음 작업의 8단계 검색 대상이 하나 늘어난다.
- 판단: 없음 — 승인이 곧 등록 조건.
- 화면: "이 사례가 지식 베이스에 등록되었습니다" 확인 표시.

## 구 10단계 대비 주요 변경점 (팀 공유용)

1. 촬영 주체: 오케스트레이터 자동 배정 → **정비사 명령형 + 오케스트레이터 실행 게이트** (배정 판단은 "이 명령을 실행해도 되는가" 게이트로 축소)
2. 직접 촬영 경로 신설: 플랫폼 카메라/스마트폰 업로드 + 로봇과 동일한 품질 검사
3. 온톨로지 → Skill 파라미터 변환 명시 (5단계): "로봇에 온톨로지가 왜 필요한가"의 실물
4. 병행 작업 명시 (6단계): 정비사는 로봇을 기다리지 않는다 — "로봇 느린데?" 방어
5. 챗봇: 작업 시작 시 1회 → **작업 전 구간 상시** (화면+음성), 집은 서버·접점은 디바이스
6. 유사 사례 제시 시점: 작업 시작 → **촬영 이후(8단계)** — 사진이 검색 입력이 되는 구조 ("실행 중 생성된 정보가 지식 검색의 입력이 된다")
7. 지식 환류의 실체 구체화 (12단계): 임베딩 인덱스 + 메타데이터 등록
8. 공구 전달 제거 → 성숙 비전으로 이동
