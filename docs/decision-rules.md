## 판단 규칙표 (판단 × 입력 × 규칙 요지 × 출력 × 실행 위치)

### 판단 ⓪ — 작업 해석·분해 (시나리오 4단계) · **Cloud**

| 항목 | 내용 |
| --- | --- |
| 입력 | Work Order(작업 종류·기체·구역), 절차 온톨로지(작업 종류→필수 검사 항목→요구 컷·주의사항·executable_by) |
| 출력 | Task Step 목록(선후관계·주체 후보·요구 컷), 타임라인 화면 |
| 위치 | Cloud — 온톨로지 전체를 봐야 하는 지식 판단의 전형 |

```txt
작업 종류를 온톨로지에서 조회
→ 필수 검사 항목 목록 획득
→ 항목별 Task Step 생성 + 선후관계 연결
→ 각 Step에 수행 주체 후보 부여 (온톨로지 executable_by 속성)
→ 요구 컷·주의사항 첨부
조회 실패(지식에 없는 작업 종류) → Task Step 생성 없이 "수동 작업 모드" 표시 + 정비사 알림
```

**발표 방어:** "워크플로우는 하드코딩이 아니라 절차 지식에서 생성됩니다 — 작업 종류가 바뀌면 단계 구성이 바뀝니다." ("Workflow 아닌가요?"의 뿌리 답변)

### 판단 ① — 실행 게이트 (시나리오 5단계) · **Cloud 작업 계획 생성 → Edge 실행 직전 검증**

| 항목 | 내용 |
| --- | --- |
| 입력 | 정비사 촬영 명령(대상 부위), 절차 온톨로지(부위→접근 방향·요구 각도·조명 여부), 로봇 텔레메트리(가용·오류 코드) |
| 출력 | Skill Request(실행 파라미터 포함) 또는 거부 + 직접 촬영 안내 |
| 위치 | **Cloud: 작업 계획 생성(Planning)** / **Edge: 실행 직전 검증** |

```txt
[Cloud — 작업 계획 생성]
촬영 명령 수신
→ 현재 Step 확인
→ 필요 절차 조회 (온톨로지)
→ 필요 Robot Skill 결정
→ 실행 파라미터 생성 (접근 방향·요구 각도·조명)
   스펙 없는 부위 → 기본 파라미터 + "표준 스펙 없음" 표시(증빙에 기록)
→ Skill Request 발행

[Edge — 실행 직전 검증]
발행된 Skill Request 수신
→ 로봇 가용성·안전 상태 최종 확인 (텔레메트리)
   통과 → 로봇 실행
   불통과 → 거부, 사유와 함께 직접 촬영 안내
```

**발표 방어:** "사람은 부위만 말하고, 어떻게 찍는지는 지식이 계획합니다 — 단순 명령 중계가 아니라 Planning입니다."

> ◆ v1.1: '부위→접근 방향·요구 각도·조명 여부'의 데이터 실체 = v3.6 **검사위치 클래스 '촬영 스펙' 속성**(🔧 팀 정의 + 2차 인터뷰 보정). 물리 근거 — 산업 육안검사 통상 기준 600mm 이내·시야각 30°↑·1,000럭스↑, 균열은 5~45° 스침 조명에서 드러남(`72_왜로봇팔인가` — 항공 GVI/DVI는 정량 미규정, '통상 기준'으로만 인용). 위 의사코드의 "스펙 없는 부위 → 기본 파라미터" 분기가 팀 정의 공백을 흡수한다.

### 판단 ② — 촬영 결과 검증 (시나리오 7단계) · **Edge 검증·재촬영 루프 → Cloud 수용 확정**

| 항목 | 내용 |
| --- | --- |
| 입력 | 신규 Evidence(사진 + 촬영 출처), 품질 검사 결과(판정은 비전 AI 모듈, 오케스트레이터는 결과값만 수신), 재시도 카운트 |
| 출력 | Evidence 수용 / 재촬영 Skill Request(파라미터 보정) / 재촬영 요청 알림 / 판단 ③ 호출 |
| 위치 | **Edge: 품질 검증·자동 재촬영 루프** (사진이 흔들렸나·초점이 맞았나·조명이 충분한가 — 원본이 엣지에 있으니 검사도 엣지, 왕복 지연 없음) / **Cloud: 수용 확정·상태 기록** |

```txt
Evidence 등록 → 품질 검사 결과 수신 [Edge]
→ 통과 → '수용' 상태 전이 [Cloud], 8단계(분석·유사 사례)로 진행
→ 미달 → 재시도 카운트 < 상한(⚙️) ?
   예 → 출처=로봇: 미달 사유를 파라미터 보정에 반영해 자동 재촬영
           (예: 조도 부족 → 조명 강화) [Edge 루프]
        출처=정비사: 미달 사유와 함께 재촬영 요청 알림
   아니오 → 판단 ③(수동 전환)으로 위임
```

**발표 방어:** 품질 *판정*은 AI, 그 결과로 뭘 할지의 *결정*은 규칙 — 3층 분리의 반복. "미달 사유→보정"은 조건을 바꿔 재시도하는 것이라 단순 retry 루프가 아님.

> ◆ v1.1: 보정 예를 하나 더 확보 — 조도 부족 → 조명 강화 외에 **각도 부적합 → 스침각 재조정**(균열은 5~45° 스침 조명에서 그림자로 드러나므로, 각도가 곧 가시성이다). / Skill Request의 온톨로지 모델링(로봇스킬 클래스와 분리할지)은 **v3.6 §8.2 온톨로지 담당 결정 대기** — 어느 쪽이든 본 규칙의 동작은 동일하다.

### 판단 ③ — 수동 전환 (시나리오 7단계) · **안전 정지 Edge → 전환 결정 Cloud**

| 항목 | 내용 |
| --- | --- |
| 입력 | 로봇 Execution Event(오류·무응답), Skill Request 경과 시간, 판단 ②의 상한 초과 위임 |
| 출력 | 안전 정지 명령, Task 모드 전환('직접 촬영'), 전환 사유 알림 + 촬영 가이드 |
| 위치 | **Edge: 안전 정지** (0.1초 판단) / **Cloud: 전환 결정·알림** (작업 전체 판단) |

```txt
트리거: 로봇 오류 이벤트 / 응답 시간초과(⚙️) / 재시도 상한 초과(②에서 위임)
→ 즉시 안전 정지 명령 [Edge]
→ 해당 촬영 Task를 '직접 촬영' 모드로 전환 [Cloud]
→ 정비사 디바이스에 전환 사유 알림 + 촬영 가이드
→ 전체 작업은 중단하지 않는다 — 해당 Task만 전환, 나머지 진행 유지
```

**발표 방어:** "로봇이 죽어도 작업은 죽지 않는다." (시연 필수 예외)

### 판단 ④ — 전이 (시나리오 10단계) · **Cloud**

| 항목 | 내용 |
| --- | --- |
| 입력 | Human Decision(정상/이상/재검사 + 사유), 현재 Task Step 위치, 잔여 Task Step 목록 |
| 출력 | 다음 Step 활성화 / 조치 기록 Step 생성 / 촬영 복귀 / 보류 / 판단 ⑤ 호출 |
| 위치 | Cloud — 작업 전체 상태를 봐야 함 |

```txt
판정 수신 →
  정상 → 잔여 Step 있음? 예 → 다음 Step 활성화 / 아니오 → 판단 ⑤ 호출
  이상 → 후속 조치 기록 Step 생성(수리 연계는 범위 밖, 기록까지만) → 잔여 Step 진행
  재검사 → 해당 부위 촬영 Task 재활성화(5단계 복귀), 재검사 사유를 가이드·파라미터에 첨부
판정 대기 시간초과(⚙️) → '보류' 표시만 (독촉·재배정 안 함 — 중앙 관리자 영역)
```

### 판단 ⑤ — 종료 (시나리오 11단계) · **Cloud**

| 항목 | 내용 |
| --- | --- |
| 입력 | 전체 Task Step 상태, Work Card 초안(필수 항목), Human Decision(승인/반려) |
| 출력 | 승인 요청 / 누락 항목 표시 / Work Record 확정·환류 트리거 / 재작성 복귀 |
| 위치 | Cloud — Work Card·환류의 중앙 판단 |

```txt
판단 ④에서 호출 →
완결성 게이트: 요구 컷별 수용 Evidence? 품질 통과? 판정 기록? 촬영 출처?
   [⚙️ 설계 반영 · PoC 미구현 — PoC는 게이트 생략, 승인 요청 직행]
   미비 → 누락 항목 표시, 승인 요청 보류
   통과 → Work Card 초안 조립 → 정비사 승인 요청
          (Record Agent: 사진·로그 정렬 + 음성메모→기록 문안 초안 생성)
승인 → Work Record 확정 → 작업 종료 → 12단계 환류(임베딩 인덱스+메타데이터 등록)
반려 → 반려 항목만 재작성 복귀 (사유 첨부)
```

## Q&A 직결 답변 (규칙표 → 발표 연결)

**"그냥 순서대로 실행하는 Workflow 아닌가요?"**

> "세 가지가 다릅니다. 첫째, 단계 자체가 하드코딩이 아니라 절차 지식에서 생성됩니다(판단 ⓪). 둘째, 실행마다 지식 기반 계획을 새로 만듭니다 — 부위가 바뀌면 로봇 Skill과 파라미터가 바뀝니다(판단 ①). 셋째, 분기점마다 상태를 읽고 규칙으로 결정합니다 — 재촬영은 조건을 보정해 재시도하고(②), 로봇이 죽어도 작업은 계속되며(③), 완결성이 검증돼야 닫힙니다(⑤). 순차 실행기는 이 중 아무것도 하지 않습니다."

**"판단을 왜 Edge와 Cloud로 나눴나요?"**

> "Edge는 반사신경, Cloud는 판단력입니다. 0.1초가 급하거나 안전이 걸리면 격납고 엣지에서, 작업 전체와 지식을 봐야 하면 클라우드에서 — 그리고 통신이 끊겨도 엣지는 스스로 안전하게 멈춥니다. 이 계층 분리를 자기 소유 엣지 인프라 위에서 설계·운영할 수 있는 사업자가 KT입니다."
